Journeys through the system

  1. Sign-in: staff open app.shriyamining.com → email + password checked by the API (PBKDF2 + secret pepper) → session cookie (HttpOnly, 60 min idle, 12 h max) → every API call checks role and permission.
  2. Invoice to buyer: staff build the invoice from POs → the browser makes the PDF → API saves it and emails the buyer through Zoho with a private review link → buyer opens /review, approves or rejects → status and history update; the staff see it at once.
  3. Insights: the proprietor opens Insights → one call to the API → five read-only procedures work out totals, pipeline, attention, buyers and shipping from the live data → every figure links to its list. Nothing runs on a timer.
  4. Archive to Drive: any status change writes a "save" task in the same database step → the browser sends the PDF → API uploads it to Invoice/Buyer/Year and moves the previous status's file to the bin. Uploaded POs go to PO's/Buyer/Year. Failures are listed with Retry and raise an alert.
  5. Images: an Admin chooses up to 30 photos → the browser fingerprints them and asks the API once about clashes (same file, same name) → each is made smaller in the browser (≤ 2560 px, ≤ 3 MB, a 400 px preview) → one API call per image stores it in the database → the grid shows previews, cached for a year. A delete never removes an image another table uses.
  6. A change reaching users: developer pushes to test → pipeline tests, migrates the test database, deploys, smoke-tests → checked on the test site → the same commit is pushed to main → production. Rollback = redeploy the previous release.

Design choices worth knowing

  1. $0-first: Free tiers everywhere; the only paid item is production database time beyond the free offer, capped by a $20 budget alert.
  2. One app, not many services: the API is a modular monolith (6 modules) inside the Static Web App — simple and free. Standby Function Apps exist (stopped) if it ever needs to be split out.
  3. Test mirrors production with its own database, settings, keys and Drive folders; production data is copied to test only on demand.
  4. Secrets only in Azure settings — never in code, never in the database, never in the public Docs repo.
  5. Heavy work in the browser (PDFs, Excel, photo resizing) keeps the server small and free.
