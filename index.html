Overview

A web application for managing export invoices: create/edit invoices, import purchase orders from Excel, generate Excel/PDF/print exports, manage company profile data, and administer users/roles. Backend is C# (.NET, Azure Functions isolated worker); frontend is Vue 3, deployed as an independent repository. Three repos, all under the shriyaminingindustriesgroup GitHub account:

Architecture

The Static Web App's co-located Functions — not the standalone Function Apps — serve 100% of real traffic. Each SWA environment gets its own private copy of the API's compiled build. The standalone Function Apps are kept deployed and healthy on purpose, as a decouple-ready fallback (see ARCHITECTURE.md §9).

Database

Two mechanisms, deliberately separate: DbUp owns tables and data (database/migrations/*.sql); a SQL Database Project owns stored procedures/views (published via SqlPackage, excluding tables/data from the diff). Schema: a security schema (User/Role/Permission, role-based) and an app schema (Vendor/Buyer/Invoice and related master data).

Authentication & authorization

Login goes through the Static Web App's built-in Entra ID auth — no custom app registration. SWA injects an x-ms-client-principal header on every authenticated request; the API's middleware decodes it and looks up roles/permissions by email against security.User. Logging in via AAD always succeeds if your identity is valid — you get zero permissions until your email exists as an active row with a role assigned. There is no self-service bootstrap for the first admin user; it's created directly via SQL (see ARCHITECTURE.md §8 for the exact script).

Cost model

Deliberately built to stay near $0/month at real usage (~5 users, max 1–2 hrs/day), verified against actual Azure pricing rather than assumed:

  • SWA Free tier — co-located Functions chosen specifically so Standard tier (~$9/mo) isn't needed.
  • Functions Consumption plan — 1M executions + 400,000 GB-s free per month, per subscription, shared across both Function Apps.
  • Both SQL databases have the Azure SQL free offer applied — 100,000 vCore-seconds + 32GB free per database per month, for the life of the subscription.

Debugging playbook

"degraded" health / Error 40613 against SQL. Serverless auto-pause after 60 min idle. First request wakes it up and reports degraded; just retry.
A route 404s with no app error envelope. Azure Functions reserves the literal path segment admin for its own internal API. That's why the admin console uses console/*, not admin/*.
AADSTS700213 on azure/login@v2. The federated identity credential doesn't have an entry for this branch yet — each long-lived branch needs its own, scoped by exact subject string.
UI deploy grabs the wrong environment's API build. Never trust "latest release" when two environments publish to the same repo — match on tag pattern instead.
Print/PDF export fails. Print layout is deliberately not served by the API — it's built entirely client-side from data already fetched. A call to ?format=print reaching the API at all is a regression.
A fresh migration run fails with "schema does not exist." Fixed once already — a repeatable (R__) script was running before the versioned (V###__) script that creates what it depends on, because DbUp's default order is plain alphabetical and "R" sorts before "V". The real Azure databases never hit this because they were seeded without actually running the scripts — only a true from-scratch run (the local Docker setup below) exercises migration order at all.
A cross-repo workflow step breaks with "Could not resolve to a Repository." The default GITHUB_TOKEN can read a public repo it doesn't belong to, but not a private one. Making ShriyaMiningIndustries_api private broke the UI repo's ability to download its releases until a dedicated read-only PAT was added.

Local development

Cloned ShriyaMiningIndustries_api and want to run it with the interactive Swagger UI? The project already ships a fully-described OpenAPI contract — no separate tool to build.

  1. Prerequisites: .NET 10 SDK, Azure Functions Core Tools v4 (npm install -g azure-functions-core-tools@4), Azurite (npm install -g azurite, run it in its own terminal), and Docker Desktop (recommended — gives you a fully isolated local database, nothing to ask anyone for).
  2. cd local-dev
docker compose up -d
    Spins up a local SQL Server container. The template below is already pre-filled to match it — no connection string to request from anyone. (Alternative: skip Docker and ask a team member for the shared shriyaminingdbtest connection string instead — never the production one — see ARCHITECTURE.md §15.2 Option B.) 
  3. cd src/ShriyaMiningIndustries.Api
cp local.settings.json.example local.settings.json
    This file is git-ignored — never commit it. 
  4. dotnet run --configuration Release
    Use dotnet run, not func start — the latter warns it may not load extensions correctly for this project. Once it's up, open http://localhost:7071/api/swagger/ui.

To test permission-gated endpoints without a real login, the template's LocalDevelopment:AutoAuthenticateAsEmail setting auto-authenticates every local request as the email you set there — double-gated so it can never activate anywhere real (only works in a local Development run, and only when this git-ignored key is present). The email still needs a real role in security.User in shriyaminingdbtest to get actual permissions (same bootstrap script as §8).

Running the UI locally, against your local API

The UI's Vite dev server already proxies /api/* to localhost:7071 — no extra config needed:

git clone .../ShriyaMiningIndustries_UI.git
cd ShriyaMiningIndustries_UI
npm install
npm run dev

Open localhost:3000 with the local API (above) running alongside it. npm run test runs the Vitest suite, npm run type-check runs vue-tsc — both run in CI on every push.

Rollback runbook

A bad deploy that passed test and still breaks in production: decide forward-fix vs. revert first — if the cause isn't obvious yet, revert, investigate after.

Code (API or UI): git revert <bad-sha> on main, push. Goes through the exact same pipeline as any other change — no separate "rollback mode."

A broken migration: DbUp is forward-only — never edit or delete an already-applied migration file. Write a new migration that undoes the specific change instead.

Stored procedures: safer — a diff-and-replace publish, not one-way, so reverting the C# source naturally republishes the previous version on the next deploy.

Full runbook, including what to check when the deploy itself isn't the problem, in ARCHITECTURE.md §16.
