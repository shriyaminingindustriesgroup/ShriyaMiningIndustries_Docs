Overview

A web application for managing export invoices: create/edit invoices, import purchase orders from Excel, generate Excel/PDF/print exports, manage company profile data, and administer users/roles. Backend is C# (.NET, Azure Functions isolated worker); frontend is Vue 3, deployed as an independent repository. Three repos, all under the shriyaminingindustriesgroup GitHub account:

Architecture

The Static Web App's co-located Functions — not the standalone Function Apps — serve 100% of real traffic. Each SWA environment gets its own private copy of the API's compiled build. The standalone Function Apps are kept, stopped (since 17 Nov 2026, not deleted), as a decouple-ready fallback (see ARCHITECTURE.md §9).

Database

One owner, DbUp (database/migrations, since 17 Nov 2026): V### scripts change tables and data and run once; R__ scripts hold every stored procedure and view and run on every deploy. (A second tool, a SQL Database Project published with SqlPackage, used to deploy a hand-copied set of procedures; it was removed.) Schema: a security schema (User/Role/Permission, role-based), an app schema (Vendor/Buyer/Invoice and related data), sales (POs) and log.

Design review (V029, 17 Nov): the invoice view no longer locks on every read; a deleted user can be added back; a deactivated buyer's code can be reused; all log tables are purged hourly (payload 30 days, errors 90 days/1 year, events 90 days, email log 1 year); status checks on the email tables; an index on every foreign key; duplicate indexes removed. The rules are in ARCHITECTURE.md §7.3.

Repositories (17 Nov): every repository is now tested against a real database built from the scripts, in CI on every push (a free, throwaway SQL Server on the runner); the first run found that a buyer with a ship-to address couldn't be deleted (fixed). A stored procedure's own message ("PO format must be Pdf or Spreadsheet") now reaches the user instead of "Invalid input provided", and repositories hand services typed errors (conflict, not found). Rules: one procedure or one transaction for anything all-or-nothing, no database call per item in a loop, one owner per table (IAppSettings for settings). ARCHITECTURE.md §7.4.

Every query is a stored procedure (18 Nov): the API's C# holds no SQL text; about 55 queries moved from 15 repositories into procedures, each reading and writing exactly what it did, and a test fails if SQL text reappears in the C#. The procedures are split one file per area (R__platform-00-shared, -10-invoices … -60-settings-logs), instead of one 2,700-line file. The standards review also added JSON checks, consistent column sizes, InvoiceDate as a date (V040), and an invoice's PO numbers as rows in app.InvoicePurchaseOrder instead of a list in one column (V041). ARCHITECTURE.md §7.1, §7.4, §7.6.

User accounts, step 1 (18 Nov, V042): each person is Invited, Active or Disabled (with who, when and why) instead of a yes/no flag. Console → Users can search and filter, turn access off (reason required) and back on, show each person's history, and export to Excel. Nobody can turn off themselves or the last active Admin. A disabled person sees "Your access has been turned off". New tables for the coming sign-in: SignInMethod, UserExternalLogin, UserChange, log.SignInEvent. ARCHITECTURE.md §7.2, §7.6, §8.

Our own sign-in, step 2 (18 Nov, V043; password only for now): a Sign in page with email and password, Forgot password (an emailed single-use link, also how people set their first password), My account (change password, sign out everywhere, recent sign-ins) and an Admin's Password link. Passwords are stored only as a salted, peppered PBKDF2 hash (the pepper is a secret app setting); the session is an HttpOnly cookie whose hash is in security.UserSession; 5 wrong passwords lock for 15 minutes. Today's Microsoft sign-in keeps working until the setting AUTH_ALLOW_PLATFORM_SIGN_IN is switched off. ARCHITECTURE.md §8.

Temporary passwords (18 Nov, V044): an Admin can give someone a random password (shown once, stored only as a hash, 72 hours); signing in with it opens only Choose your password until the person sets their own. ARCHITECTURE.md §8.

All-or-nothing procedures (18 Nov): every procedure that writes sets XACT_ABORT ON and puts several writes in one transaction, so a failure half way can't save half a change; a test enforces it. ARCHITECTURE.md §7.3.

Role cache (18 Nov): a person's roles and permissions are kept 30 seconds per API instance instead of being read on every call; any Admin change clears it. ARCHITECTURE.md §8.

Coding standards and module split (18-19 Nov): the build enforces the .NET analyzers and code style with warnings as errors; every paged list answers { items, total, pagination }; the Invoice module was split into Invoice, MasterData and Notifications (dependencies one way). Every change follows the checklist in ARCHITECTURE.md §7.8. ARCHITECTURE.md §7.7, §7.8.

Tracking → Product groups PO lines on the SKU without its delivery prefix (BED-GRNABSBLK1224FL and GRNABSBLK1224FL are one product, with a chip per delivery place). The prefixes are the itemStartsWith values of the buyer's delivery rules, removed only before a dash, and worked out when Tracking reads the data, so nothing is stored or backfilled. Everything else keeps the SKU as printed. See ARCHITECTURE.md §7.2.

Email (V024): Admin → Company profile → Services lists the email identities the system sends as (From / To / CC per service; the Invoice Email Service's To comes from each buyer), and each buyer has an invoice email list (To / CC / BCC). Email goes through one sender interface: Zoho Mail over SMTP today, Microsoft 365 (Graph) later by changing the EMAIL_PROVIDER app setting. Mailbox passwords are app settings only. See ARCHITECTURE.md §7.2 and §11.

Photos in the email (V027): the Save and send email popup can attach photos from the computer. The browser compresses them to fit (1600 px JPEG, quality stepped down as needed; iPhone HEIC photos converted in the browser, location data removed); at most 20 photos and 10 MB per email, invoice PDF included (setting EMAIL_MAX_ATTACHMENTS_MB; 3 MB automatically with Microsoft 365). The photos go to everyone on the email but aren't stored: only their names, sizes and fingerprints are listed on the Buyer approval card. Public /privacy and /terms pages back the Google Drive sign-in (20 Nov).

Invoice and PO archive (21 Nov): every status change saves the invoice's PDF to Google Drive as Invoice / Buyer / 2026 / Invoice_22_InReview_11212026111123.pdf and moves the previous status's file to the bin, so only the latest stays (year = the financial year of the invoice date, from 1 April, configurable). Every uploaded PO file, as uploaded, goes to PO's / Buyer / 2026 / PO_Buyer_time.xlsx. The status change records the save in the same transaction; the browser sends the PDF; a buyer's email decision reuses the kept PDF. Nothing of the email (PDF, photos) is saved any more.

Brand and installable app (22 Nov): a serif S monogram over a gold rule (with MINING on the larger icons) is the tab icon, header tile and home-screen icon; manifest.json and a service worker that caches nothing make the app installable on phones, tablets and computers.

Phones and tablets (21 Nov): every screen fits iPhone, iPad, Samsung Tab and laptop screens: the menu folds behind Menu under 1100 px, wide tables scroll inside their box, toolbars wrap instead of overlapping, and text boxes are 16 px on touch screens so Safari doesn't zoom. Checked at 11 widths from 360 to 1920 px. This is the standard for every UI change from now on (ARCHITECTURE §7.9): npm run check:devices opens every screen at all 11 widths before a release.

Photo folders (20 Nov): Add photos ▾ in the send pop-up also offers the Google Drive folders an Admin set up (Cloud storage → Photo folders: paste the link, Check and save). A picker shows the images newest first with thumbnails; the app reads the folders with its own read-only photo reader (a Google service account the folders are shared with), so senders never sign in.

Black and white (17 Nov): the email to the buyer looks like an ordinary business email (details table, black Review and approve invoice button, then the sign-off), and the invoice, packing list and PDF use black and light greys only, for black-and-white printers. Emails are signed with the From name set on Company profile → Services (V028).

Payload log (V026): API calls that fail (status 400 and above) are stored with their request and response for 30 days, then deleted by the API itself (at most hourly, in small batches; Static Web Apps has no timers). Successful calls can be logged too, but that switch is off. Secrets are never stored (login headers, review tokens, one-time codes read [redacted]) and files appear only as size + SHA-256. Each error log row links to the payload of the call that raised it. Admin → Payload logs shows them and holds the switches. See ARCHITECTURE.md §7.2.

Emailing invoices for approval (V025): choosing In Review turns Save into Save and send email: a PDF of the invoice is built in the browser and emailed, each To person with their own link (only a hash of it is stored), CC/BCC a copy without links; the invoice moves to In Review only once a To address got it. The buyer's page /review needs no login: approve (shipping reference) or reject (remarks), once, while the invoice is unchanged since it was sent; the decision moves the status through the normal rules, recorded as "Buyer email". Approved now needs only the shipment number; the container no. is needed from Ready to Ship. See ARCHITECTURE.md §7.2, §8.

Authentication & authorization

Our own sign-in (since 18 Nov 2026): email and password on /sign-in, Forgot password by emailed link, Admin Password link and Temporary password; the session is an HttpOnly, SameSite=Strict cookie (smi_session, stored only as a hash); changing requests must send X-Requested-With: smi. Cookies use Max-Age only and are set before the response body (the Static Web App drops anything else).

During the changeover today's Microsoft sign-in still works (setting AUTH_ALLOW_PLATFORM_SIGN_IN): SWA injects an x-ms-client-principal header and the API looks up roles/permissions by email against security.User. Either way you get zero permissions until your email is an Active user with a role. There is no self-service bootstrap for the first admin user; it's created directly via SQL (see ARCHITECTURE.md §8 for the exact script).

Refresh test data from production

Replaces test's business data (invoices, purchase orders, buyers, vendors, …) with production's. Test keeps its own users, passwords, settings, mail settings and logs. One transaction: a failed run leaves test unchanged. Tell testers before a real refresh. All of this is in the API repo on GitHub; nothing in Azure.

Refresh now

  1. API repo → Actions → Refresh test data from production → Run workflow.
  2. Branch main; tick Dry run to only check (changes nothing), untick for a real refresh; mode variable.
  3. Run workflow, open the run: about 3–4 minutes. Green: the summary lists every table and row count. Red: test is unchanged; the Refresh step says why (ARCHITECTURE.md §12.2).

Terminal: gh workflow run refresh-test-data.yml --ref main (add -f dry_run=true to only check). On demand runs even when the schedule is off or paused.

Cost model

Deliberately built to stay near $0/month at real usage (~5 users, max 1–2 hrs/day), verified against actual Azure pricing rather than assumed:

  • SWA Free tier — co-located Functions chosen specifically so Standard tier (~$9/mo) isn't needed.
  • Functions Consumption plan — 1M executions + 400,000 GB-s free per month, per subscription, shared across both Function Apps.
  • Both SQL databases have the Azure SQL free offer applied — 100,000 vCore-seconds + 32GB free per database per month, for the life of the subscription.
  • Test-data refresh — GitHub Actions minutes within the free allowance; the databases are awake only while it runs.

Operations

Everything here is free (Application Insights used 0.56 GB of its free 5 GB a month on 18 Nov; daily cap 0.3 GB).

  • Admin → Health: tiles for 24 hours / 7 days / 30 days with targets (green or amber), every sign-in and every email with the mail server's answer. From the app's own logs.
  • Alerts (email, 6 metric rules): exception spike, failed requests, invoice email all failed, account email failed, sign-in locked, refused sign-ins burst. What to do for each: ARCHITECTURE.md §12.1.

  • Test data from production: the Refresh test data from production workflow (API repo), on a schedule or on demand; runbook in ARCHITECTURE.md §12.2.

Debugging playbook

Signed in, but the sign-in page comes back with no error. The Static Web App drops a Set-Cookie that has Expires, and a cookie set after the response body started is lost: use Max-Age only and set cookies first. See ARCHITECTURE.md §12.
"degraded" health / Error 40613 against SQL. Serverless auto-pause after 60 min idle (that's what keeps it free; no keep-alive pings). The app handles the wake-up itself: the API waits up to 30 s while opening the connection, then answers 503 DB-WAKING-503; the UI shows "Waking up the database…" and retries for up to 90 s. See ARCHITECTURE.md §12.
A route 404s with no app error envelope. Azure Functions reserves the literal path segment admin for its own internal API. That's why the admin console uses console/*, not admin/*.
AADSTS700213 on azure/login@v2. The federated identity credential doesn't have an entry for this branch yet — each long-lived branch needs its own, scoped by exact subject string.
UI deploy grabs the wrong environment's API build. Never trust "latest release" when two environments publish to the same repo — match on tag pattern instead.
Print/PDF export fails. Print layout is deliberately not served by the API — it's built entirely client-side from data already fetched. A call to ?format=print reaching the API at all is a regression.
Excel export 400s for a PO-editor (document) invoice. Same principle as print: document invoices' Excel workbook is built entirely client-side by the same code that renders the on-screen preview, so the file can never drift from the preview. The API's export endpoint only serves simple items-based invoices — route the call site to the client-side builder, don't port the layout into C#.
A fresh migration run fails with "schema does not exist." Fixed once already — a repeatable (R__) script was running before the versioned (V###__) script that creates what it depends on, because DbUp's default order is plain alphabetical and "R" sorts before "V". The real Azure databases never hit this because they were seeded without actually running the scripts — only a true from-scratch run (the local Docker setup below) exercises migration order at all.
A cross-repo workflow step breaks with "Could not resolve to a Repository." The default GITHUB_TOKEN can read a public repo it doesn't belong to, but not a private one. Making ShriyaMiningIndustries_api private broke the UI repo's ability to download its releases until a dedicated read-only PAT was added.

Local development

Cloned ShriyaMiningIndustries_api and want to run it with the interactive Swagger UI? The project already ships a fully-described OpenAPI contract — no separate tool to build.

  1. Prerequisites: .NET 10 SDK, Azure Functions Core Tools v4 (npm install -g azure-functions-core-tools@4), Azurite (npm install -g azurite, run it in its own terminal), and Docker Desktop (recommended — gives you a fully isolated local database, nothing to ask anyone for).
  2. cd local-dev
docker compose up -d
    Spins up a local SQL Server container. The template below is already pre-filled to match it — no connection string to request from anyone. (Alternative: skip Docker and ask a team member for the shared shriyaminingdbtest connection string instead — never the production one — see ARCHITECTURE.md §15.2 Option B.) 
  3. cd src/ShriyaMiningIndustries.Api
cp local.settings.json.example local.settings.json
    This file is git-ignored — never commit it. 
  4. dotnet run --configuration Release
    Use dotnet run, not func start — the latter warns it may not load extensions correctly for this project. Once it's up, open http://localhost:7071/api/swagger/ui.

To test permission-gated endpoints without a real login, the template's LocalDevelopment:AutoAuthenticateAsEmail setting auto-authenticates every local request as the email you set there — double-gated so it can never activate anywhere real (only works in a local Development run, and only when this git-ignored key is present). The email still needs a real role in security.User in shriyaminingdbtest to get actual permissions (same bootstrap script as §8).

Rollback runbook

A bad deploy that passed test and still breaks in production: decide forward-fix vs. revert first — if the cause isn't obvious yet, revert, investigate after.

Code (API or UI): git revert <bad-sha> on main, push. Goes through the exact same pipeline as any other change — no separate "rollback mode."

A broken migration: DbUp is forward-only — never edit or delete an already-applied migration file. Write a new migration that undoes the specific change instead.

Stored procedures: safer — a diff-and-replace publish, not one-way, so reverting the C# source naturally republishes the previous version on the next deploy.

Full runbook, including what to check when the deploy itself isn't the problem, in ARCHITECTURE.md §16.

Onboarding a new developer (with AI assistance)

Both repos carry two auto-loaded context files — CLAUDE.md and .github/copilot-instructions.md — both pointing back at this document. A new developer using Claude Code or GitHub Copilot gets the full architecture context automatically, nothing to paste in by hand.

  1. Get added as a collaborator — both repos are private.
  2. Clone, then follow the README's local-dev quick start (Docker-based, nothing to ask anyone for).
  3. Branch off test, not main.
  4. Open the repo in Claude Code or VS Code + Copilot — context loads automatically.
  5. Describe the feature in plain language; ask for a plan before code on anything non-trivial.
  6. Test locally, push the feature branch, PR into test, validate there, then merge test → main.
